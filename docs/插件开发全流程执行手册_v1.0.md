## 摘要

这是一份面向单人开发者和小团队的**执行手册**，不是方法论综述。它把通用的软件开发生命周期（ISO/IEC/IEEE 12207 的过程视角）压缩成一条能走完的流水线：每个阶段都有明确产出、通过条件和证据要求。安全相关活动对齐 NIST SSDF 的四组实践：准备组织、保护软件、生产安全的软件、响应漏洞。

插件与普通应用最大的差别是：代码运行在别人的宿主里，直接接触用户的学习记录或文献库，升级由宿主版本决定，出了事用户先感知。因此本手册把**兼容、数据安全、回滚、五层验证**放在比“功能速度”更高的位置。

> **三条硬规则**
>
> 1. 用户数据只读优先；任何写入前先备份，一次只做一个破坏性动作。
> 2. 源码、测试、已部署、已加载、屏幕五层分开报告；缺一层证据，就不能说“完成”。
> 3. 先设计回滚，再设计功能；没有回滚方案的发布不算发布。

## 0. 这份手册怎么用

本手册假设你是“一个人同时扮演产品、开发、测试、发布、运维”的角色。它不要求你每天填一堆表，而是要求你在四个关键时刻停下来，留下可复核的证据：

1. **动手前**：问题是否真实、基线是否可量化（需求门 G1）。
2. **写代码前**：数据怎么改、兼容怎么保、出事怎么退（设计门 G2）。
3. **部署前**：单测、契约、离屏 UI、真机、性能是否都有证据（质量门 G3）。
4. **说“完成”前**：是否真的装上了、加载了、屏幕上对了（上线门 G4）。

> 不替代官方文档。Anki/Zotero 的 API、清单字段、打包规则以其官方文档为准；本手册解决的是“怎么把事做完整、可验证、可回滚”。

### 五层模型

| 层 | 回答的问题 | 典型证据 | 常见假成功 |
|---|---|---|---|
| 源码 | 改的是不是这个分支、这个文件？ | `git status`、`git log -1`、diff | 改在 worktree，部署的是旧目录 |
| 测试 | 逻辑、契约、UI、性能是否通过？ | 测试输出、probe 报告 | 单测绿，但集成没跑 |
| 已部署 | 目标目录里的文件是不是新的？ | SHA-256、修改时间 | 拷错目录、漏拷数据文件 |
| 已加载 | 宿主进程是否加载了新代码？ | 启动日志、加载时间、版本号 | 没重启，Python 模块缓存仍旧 |
| 屏幕 | 用户实际看到的行为对不对？ | 截图/录像、用户确认 | UI 状态或数据不对 |

**报告规则**：任何一层没有证据，就写“未验证”，不要用“应该没问题”替代。

## 1. 全流程总览：十个阶段，四道门

流程不是瀑布。实际执行时允许小步迭代，但四道门不能跳：

- **G1 需求门**：确认“做对的事”。
- **G2 设计门**：确认“知道怎么退”。
- **G3 质量门**：确认“证据够”。
- **G4 上线门**：确认“装上了、加载了、用户看到了”。

| 阶段 | 核心问题 | 必须产出 | 通过条件 |
|---|---|---|---|
| 0 立项 | 解决谁的什么问题？ | 问题陈述、基线数据、风险初筛 | 问题可复现，基线可量化 |
| 1 需求 | 做到什么算对？ | 用户故事、验收标准、非目标 | 每条验收都可测 |
| 2 设计 | 怎么改、怎么退？ | 设计说明、兼容矩阵、回滚方案、ADR | 风险有缓解，回滚可执行 |
| 3 环境 | 在哪改、怎么集成？ | 分支、隔离环境、CI | 主干可构建，测试不碰真实数据 |
| 4 实现 | 代码是否最小、可读、可测？ | 小步提交、单测、日志 | 提交可构建，测试随代码走 |
| 5 测试 | 证据够不够？ | 单测、契约、离屏 UI、E2E、性能报告 | 质量门全绿，反证成立 |
| 6 部署 | 装到哪、加载了吗？ | 备份、哈希、重启记录、计数指纹 | 前四层都有证据 |
| 7 验收 | 用户真的看到了吗？ | 验收记录、截图/日志、性能数据 | 屏幕层通过，用户确认 |
| 8 发布 | 别人能装吗？ | 版本、安装包、变更日志、校验和 | 干净环境可安装、可回滚 |
| 9 运维 | 坏了怎么办？ | 监控、告警、回滚演练 | MTTR 可度量 |
| 10 复盘 | 下次怎么更好？ | 复盘、改进项、交接包 | 改进项有负责人和期限 |

**单人团队怎么执行门禁？** 用“自证 + 证据”替代同事评审：每道门在 issue 或 PR 里贴一条证据（测试输出、哈希、日志、截图），而不是口头说“测过了”。证据必须能被下一个接手的人复核。

## 2. 阶段 0：立项与问题定义

立项不是写一份宏大方案，而是把“值得做”变成“可验证”。先回答六个问题，再决定是否动代码。

- **现状**：谁在什么场景下遇到什么问题？出现频率多高？
- **证据**：日志、截图、计时、用户原话；不要用“感觉慢”“应该有用”。
- **影响**：影响多少用户、多少数据、是否阻断学习或写作。
- **非目标**：这次明确不做什么，防止范围蔓延。
- **约束**：宿主版本、操作系统、网络、隐私、许可、时间。
- **成功指标**：一个可量化的主指标，加一个防回退指标。

### 基线测量

没有基线就没有优化：先测再改，改完用**同一脚本、同一数据集**复测。基线至少记录五项：

- 版本：宿主版本、插件 commit、关键配置。
- 数据规模：卡片、笔记、牌组、文献条目数量。
- 性能：关键路径 p50/p90、往返次数、冷启动耗时。
- 错误：日志中的异常计数与最近一次故障。
- 复现：最小、可重复的步骤，最好附脚本。

> **反例**：直接说“评分后很卡，我来优化”。没有基线，改完只能凭感觉说“好像快了”。正确做法是先跑同一路径 10 次，记录 p50/p90 和调用次数，再动手。

**本项目示例（2026-11-12 快照）**：在真实合集上，`prepare_question` 的往返次数从 11 次（9–13）降到 6–7 次，p50 从约 1083 ms 降到约 763 ms；冷启动第一张从 13 次/1752 ms 降到 8 次/1483 ms。这个结果之所以可信，是因为改动前后用的是同一个只读 probe、同一套捕获数据。

## 3. 阶段 1：需求与验收标准

需求的最小单位是“一条可验收的行为”，不是“一个功能模块”。每条需求同时写正常路径、边界路径、失败路径，否则测试阶段一定会漏。

- **用户故事**：作为（角色），我希望（行为），以便（价值）。
- **验收标准**：Given（前提）/ When（动作）/ Then（可观察结果）。
- **非功能**：性能预算、兼容范围、隐私、离线能力、可访问性、国际化。
- **非目标**：明确不承诺的能力，避免用户预期错位。
- **可观测**：每条验收对应一个证据（测试名、日志、截图、指标）。

| 需求类型 | 示例 | 验收证据 |
|---|---|---|
| 功能 | 评分后 300 ms 内出现下一张 | 录像加时间戳 |
| 性能 | `prepare_question` p90 ≤ 1200 ms | 同一数据集上的 probe 报告 |
| 兼容 | Anki 26.x、Zotero 7.x 可加载 | 版本矩阵记录 |
| 数据 | 部署前后计数完全一致 | `verify-state` 输出 |
| 安全 | 日志不含卡片正文和密钥 | 日志抽样加代码审查 |
| 可用性 | 首次使用无需读文档 | 5 人可用性测试记录 |

### Definition of Ready（DoR）

- [ ] 问题陈述能在一页内说清
- [ ] 每条验收都有正常/边界/失败三种情况
- [ ] 性能与兼容写成了数字或版本范围
- [ ] 非目标已明确
- [ ] 已有基线或可重复的复现步骤

五条不齐，不进入设计。

## 4. 阶段 2：设计与风险

设计文档不需要长，但必须让另一个人能据此判断“会不会炸、炸了怎么退”。最少包含六个部分：

- **边界**：哪些模块改、哪些不改；调用方向和数据流。
- **数据**：读写哪些字段；是否迁移；迁移失败怎么恢复。
- **接口**：宿主 API、外部服务、超时、重试、降级。
- **并发**：UI 线程与后台线程的分工；锁、幂等、取消。
- **兼容**：宿主版本、操作系统、Python/Node 版本。
- **回滚**：备份点、功能开关、旧版本安装包。

### 风险登记表

| 风险 | 触发信号 | 缓解 | 回滚 |
|---|---|---|---|
| 宿主升级 | 启动报错、钩子失效 | 兼容矩阵加启动自检 | 保留旧版安装包 |
| 数据损坏 | 计数变化、异常写入 | 只读优先、备份、事务 | 还原备份 |
| 性能回退 | p90 超预算 | 基线加 probe 加预算门 | 回退上一版 |
| 外部服务失败 | 超时、限流、鉴权失败 | 超时、重试、缓存、降级 | 关闭该功能 |
| 供应链 | 依赖漏洞、恶意包 | 锁版本、审计、最小依赖 | 移除依赖 |
| 发布包污染 | 包含密钥或 `__pycache__` | 打包脚本加白名单 | 重新打包 |
| 回滚失败 | 还原后仍报错 | 回滚演练加校验和 | 全新安装加导入备份 |

每个影响架构或数据的选择，写一条 **ADR**（Architecture Decision Record）：背景、决策、备选、后果、回滚。ADR 的价值不在“显得专业”，而在半年后还能解释为什么这样写。

> **先设计回滚，再设计功能。** 回滚方案必须写成可执行步骤，而不是“到时候再说”。回滚演练过一次，才算真的有回滚方案。

## 5. 阶段 3：环境、分支与 CI

插件开发最常见的“假成功”是：代码在源码目录里对，测试也绿，但装进宿主后加载的是旧模块。环境设计的目标就是让五层各自可验证。

### 环境隔离

- 真实账户**只读**；需要写入时用测试账户、测试牌组或测试资料库。
- Anki：独立测试 profile 或测试牌组；操作前备份 collection。
- Zotero：独立 data directory；不要在主库上试数据迁移。
- 固定工具链版本（Python、uv、Node），写进 README。
- 外部服务用 mock 或录制的响应；离线也能跑测试。

### 分支模型

采用 **GitHub Flow**：`main` 永远可发布；从 `main` 拉短分支；提交后开 PR；CI 通过、描述完整再合并；合并即部署或打 tag 发布。分支生命周期控制在两天内，减少合并地狱。

| 分支 | 用途 | 合并方式 |
|---|---|---|
| `main` | 可发布主线，受保护 | 只接受 PR |
| `feat/*` | 新功能 | squash merge |
| `fix/*` | 缺陷修复 | squash merge |
| `chore/*` | 构建、文档、依赖 | squash merge |
| `release/*` | 发布稳定化（可选） | merge 后打 tag |

提交信息用 **Conventional Commits**：`type(scope): description`，例如 `fix(review): batch deck stats into one multi`。类型至少区分 `feat`、`fix`、`test`、`docs`、`chore`、`refactor`。它让 changelog 和版本号可以自动生成，也让回滚时能快速定位。

### CI 流水线

- 必跑：格式/静态检查、单元测试、Node 测试、构建/打包。
- 构建产物必须带校验和，避免“本地能装、下载损坏”。
- 依赖审计作为告警；高危漏洞必须处理。
- **CI 只证明“能构建、单测过”，不证明宿主里能用**；后者必须真机验证。

> 密钥、令牌、个人数据目录不进仓库，也不进构建缓存。CI 日志里不打印配置全文；需要排查时打印键名，不打印值。

## 6. 阶段 4：实现

实现阶段的目标不是“写完”，而是“写成能被验证的样子”。小步提交，每次提交都能构建；提交信息写“为什么”，diff 本身说明“是什么”。

### 编码规则

- 纯函数优先；I/O 放在边界；错误信息要能定位到模块和动作。
- 日志分级；默认不记录用户内容、查询词、卡片正文。
- 不在 UI 线程做同步网络或磁盘重活；长任务可取消。
- 任何缓存都要有失效策略、容量上限和观测点。
- 兼容判断集中到一层，禁止在业务代码里到处写版本 `if`。

### 插件特有的三条

1. **清单文件版本与代码版本一致**：manifest、release tag、changelog 三处对齐。
2. **生命周期钩子幂等**：重复 startup 不重复注册；注册前判断，保存句柄以便注销。
3. **shutdown/uninstall 清理**：定时器、钩子、窗口、文件句柄、临时文件、托盘图标。

配置读取提供默认值；配置结构变化要版本化迁移。升级和降级路径都要测，不能只测全新安装。

### 性能实现

先看调用次数，再看单次耗时。典型问题是 **N+1**：对每个 deck、每张卡、每个字段各发一次请求。

- 先发现候选集合，再对候选做一次批量读取；不要对未知集合做全量统计。
- 能批量的批量，能预取的预取，能缓存的缓存。
- 缓存必须区分会话内与跨会话，并明确 TTL。
- 缓存键要包含影响结果的配置和数据版本，避免脏读。
- 每次优化后，用同一 probe 复测往返数与 p50/p90，保留 before/after 输出。

### 安全实现

- 所有外部输入当不可信：deck 名、搜索词、HTML、文件名、外部 API 响应。
- 搜索查询要转义；HTML 用文本节点而不是字符串拼接。
- 网络默认关闭或明确告知；API key 存本地配置，不进日志。
- 依赖最小化；锁文件；定期审计。

## 7. 阶段 5：测试与质量门

测试按“离代码越近越便宜”分层，但**下层绿不能替代上层绿**。插件至少要覆盖五层：单元、契约、离屏 UI、真机端到端、性能。

| 层级 | 范围 | 工具 | 通过标准 |
|---|---|---|---|
| 单元 | 纯逻辑、解析、评分、格式化 | pytest / unittest | 关键分支覆盖，失败可定位 |
| 契约 | AnkiConnect/Zotero API 形状 | fake / mock | 请求数、参数、降级正确 |
| 离屏 UI | Qt 控件、弹窗、布局 | offscreen Qt | 不崩溃，关键文案与状态正确 |
| 端到端 | 真机加测试数据 | 脚本加人工 | 五层证据齐全 |
| 性能 | 同一数据集的关键路径 | probe | p50/p90、往返数达标 |
| 探索 | 异常、边界、兼容 | 人工 | 有记录，有 issue |

### 反证

去掉修复，测试必须红；恢复修复，测试必须绿。新测试先在旧代码上失败，避免“测试跟着实现写”。性能修复要保留同一脚本的 before/after 输出。

### 测试数据规则

- 不碰真实学习历史；需要写入时用副本或测试库。
- 测试结束清理测试牌组、笔记和临时文件，避免污染统计。
- 录制真实 API 响应时脱敏，移除令牌、正文和个人信息。
- 测试失败先复现，再判断是实现错、测试错还是环境错。

### 性能预算（本项目当前）

| 指标 | 预算 | 采集方式 |
|---|---|---|
| `prepare_question` p50 | ≤ 800 ms | probe 12 次 |
| `prepare_question` p90 | ≤ 1200 ms | probe 12 次 |
| 往返次数 | ≤ 8 | probe 计数 |
| 冷启动第一张 | ≤ 1.5 s | 清缓存后 probe |
| 主线程阻塞 | 无 > 300 ms | 日志加手动观察 |
| 数据计数 | 部署前后完全一致 | `verify-state` |

> 这些数字是“预算”，不是永远的目标。数据规模、宿主版本、硬件变化后要重新基线；关键是**同一条件下可比**。

### 质量门清单

- [ ] 单元测试全绿
- [ ] Node/契约测试全绿
- [ ] 离屏 UI 无崩溃
- [ ] 真机端到端通过
- [ ] 性能达到预算
- [ ] 反证成立
- [ ] 日志无新增异常
- [ ] 回滚步骤已演练

## 8. 阶段 6：部署（本地插件）

本地部署是事故高发区，因为它同时改变代码、配置和数据。原则是：**先备份、只拷贝变更、校验哈希、正常退出、确认加载、核对计数**。每一步都留下输出。

### 部署步骤

1. 确认宿主空闲：没有正在复习、同步或导出。
2. 备份到 `pre-deploy-<时间戳>/`，包含代码、配置和词库/数据文件。
3. 只拷贝本次变更的文件，保留用户配置和词库。
4. 校验源文件与目标文件哈希；数据文件单独校验。
5. 通过托盘协议或正常关闭退出宿主，不要强杀进程。
6. 启动宿主，确认加载时间晚于文件修改时间。
7. 运行 `verify-state`，部署前后计数必须一致。
8. 跑冒烟路径：打开复习、评分、下一张、关闭重开。

> **计数不变是只读部署的硬证据。** 计数一旦变化，先回滚，再分析；不要在真实数据上“边看边修”。

### 回滚步骤

1. 停止宿主。
2. 整目录还原备份，不要只挑几个文件。
3. 校验还原后的哈希。
4. 启动并确认版本与加载日志。
5. 复跑计数与冒烟，记录事故与时间线。

**本项目示例**：部署前生成 `pre-deploy-YYYYMMDD-HHMMSS` 备份；部署后比对顶层文件和数据目录哈希；用正常托盘协议退出，记录“closed politely in X s”；启动后确认加载时间晚于文件时间；最后核对 `book cards / book learned / mastered / total notes` 四项计数。任何一项变化都触发回滚。

## 9. 阶段 7：真机验收与五层证据

“装上了”不等于“加载了”，“加载了”不等于“屏幕上对”。验收时按五层逐层记录，任何一层缺失都要标成未验证，而不是默认通过。

| 层 | 看什么 | 证据 | 失败含义 |
|---|---|---|---|
| 源码 | 分支、HEAD、未提交文件 | `git status/log` | 改动没进对分支 |
| 测试 | 单测、契约、UI、性能 | 测试输出 | 代码对但集成错 |
| 已部署 | 目标文件哈希、时间 | 哈希对比 | 装错目录或漏文件 |
| 已加载 | 启动日志、加载时间、版本 | 日志 | 宿主没重启或缓存旧模块 |
| 屏幕 | 用户实际看到的行为 | 截图/录像/确认 | UI 状态或数据不对 |

### 验收脚本

- 冷启动 → 打开复习 → 评分 → 下一张 → 关闭重开。
- 边界：空牌组、缺字段、超长单词、断网、宿主升级。
- 性能：连续 10 张，记录 p50/p90 与往返数。
- 数据：评分后计数与历史符合预期，不重复、不丢失。
- 视觉：长词分音节、弹窗不遮挡、深浅色主题正常。

只让用户拍板不可逆或有体验取舍的事；其余自己验证并汇报。汇报时先给结论，再给证据，最后给未验证项和下一步。

## 10. 阶段 8：发布

发布的对象是“别人能安装的包”，不是工作目录的压缩。版本号遵循 **SemVer**：修 bug 升 PATCH，兼容新增升 MINOR，破坏性变更升 MAJOR。manifest、tag、changelog 三处版本必须一致。

- 变更日志按 **Added / Changed / Deprecated / Removed / Fixed / Security** 分类。
- release notes 写清升级注意事项、兼容范围和回滚方式。
- 包内只放运行所需文件；测试、日志、密钥、缓存一律排除。
- 生成 SHA-256，随 release 一起发布。

| 检查项 | 动作 | 证据 |
|---|---|---|
| 版本号 | manifest 与 tag、changelog 比对 | 三方一致 |
| 变更日志 | 用户可读，含升级注意 | changelog diff |
| 包内容 | 按白名单解压核对 | 文件清单 |
| 排除项 | 无 `__pycache__`、测试、密钥 | 扫描结果 |
| 全新安装 | 干净 profile 或资料库 | 安装成功截图 |
| 覆盖升级 | 旧版升到新版 | 升级后冒烟 |
| 回滚 | 旧包可装回 | 降级测试 |
| 校验和 | 下载后校验 SHA-256 | 校验输出 |

### 打包要点

**Anki**：`.ankiaddon` 本质是 zip；入口 `__init__.py`，清单 `manifest.json`；外部分发时 manifest 至少包含 `package` 和 `name`，可选 `conflicts`、`mod`；AnkiWeb 不接受含 `__pycache__` 的包。

**Zotero 7**：`.xpi` 需要 `manifest_version: 2` 和 `applications.zotero`；`bootstrap.js` 导出 `install`、`startup`、`shutdown`、`uninstall` 四个生命周期函数；`strict_max_version` 设为已测试的最新次版本。

> 发布前问自己：一个从没装过的人，能不能只按 README 在干净环境装成功？如果不能，包还没做完。

## 11. 阶段 9：运维与事件响应

本地插件没有服务端大盘，运维靠三件事：**可诊断的日志、可回滚的版本、可复现的用户报告**。

### 日志与监控

- 结构化日志：时间、级别、模块、事件、耗时。
- 默认不记录卡片正文、文献全文、密钥。
- 启动自检：版本、配置、依赖、数据目录可写。
- 日志轮转与上限；提供“导出诊断包”入口。
- 关注启动失败、异常计数、同步失败、关键路径 p90。
- 每季度做一次恢复演练：从备份还原到可用。

### 事件分级

| 级别 | 例子 | 动作与时限 |
|---|---|---|
| P0 | 数据损坏、无法启动 | 立即回滚加备份，15 分钟内止损 |
| P1 | 核心功能不可用 | 回滚或热修，1 小时内 |
| P2 | 性能明显退化 | 回退或降级，24 小时内 |
| P3 | 文案、样式 | 排期修复，下周 |

### 回滚决策

1. 数据安全优先于功能：能回滚先回滚。
2. 不能回滚时，先禁用入口或降级，再定位。
3. 保留现场：日志、版本、配置、数据快照。
4. 复盘写根因、影响、处置和防再发。
5. 改进项必须有负责人和期限。

## 12. 阶段 10：文档与交接

文档的目标是“下一个人能接手”，不是“显得完整”。最少维护四份：

- **README**：怎么装、怎么测、怎么回滚。
- **CHANGELOG**：用户可读的变更记录。
- **ADR**：为什么这样设计。
- **运行手册**：备份位置、日志位置、常见故障。

### 交接包

- 分支与 commit。
- 部署路径与当前版本。
- 备份位置与最近一次可用备份。
- 已知问题、未验证项。
- 下一步与负责人。

> 交接验收：新人按文档从零装一次，卡住的地方就是文档缺口。

## 13. 插件开发专属规则

### 13.1 Anki 插件

- **目录**：`addons21/<package>/`；入口 `__init__.py`；清单 `manifest.json`。
- **钩子**：`aqt.gui_hooks`；注册前判断，保存句柄，shutdown 时注销。
- **配置**：`mw.addonManager.getConfig(__name__)`；提供默认值与版本化迁移。
- **打包**：`.ankiaddon`；AnkiWeb 拒绝 `__pycache__`；外部分发 manifest 至少 `package`/`name`。
- **调试**：优先重启宿主；用隔离 profile；日志与版本一起记录。
- **兼容**：声明 min/max 版本；宿主升级后先跑启动自检和冒烟。

### 13.2 Zotero 7 插件

- `manifest_version: 2`；`applications.zotero` 必须有 `id`、`update_url`、`strict_min_version`、`strict_max_version`。
- `bootstrap.js` 导出 `install/startup/shutdown/uninstall`；按 reason 分支处理启用、禁用、升级、降级。
- `startup` 做全局初始化；`shutdown` 清理；窗口相关注册放在应用初始化之后。
- `prefs.js` 提供默认值；通过 `Zotero.Prefs` 读写。
- XPI 打包；`updates.json` 可在不改包的情况下更新兼容范围。
- 不直接写 SQLite；用 Zotero API 和事务；迁移前备份。

### 对比

| 对比项 | Anki | Zotero 7 |
|---|---|---|
| 清单 | `manifest.json` | `manifest.json`（v2） |
| 生命周期 | 启动时加载 Python 模块 | `bootstrap` 四钩子 |
| UI 扩展 | PyQt 与 `gui_hooks` | 窗口/DOM 注入 |
| 配置 | `addonManager` | `prefs.js` / `Zotero.Prefs` |
| 打包 | `.ankiaddon` | `.xpi` |
| 分发 | AnkiWeb / GitHub | zotero.org / GitHub |
| 兼容声明 | min/max point version | `strict_min/max_version` |
| 卸载清理 | 删目录并重启 | `shutdown/uninstall` |

## 14. 数据安全红线

1. 不直接改宿主数据库文件；用宿主 API 或事务。
2. 写入前备份；一次只做一个破坏性动作。
3. 不伪造 FSRS/复习记录；不覆盖用户学习历史。
4. 不把真实用户内容发到外部服务，除非用户明确同意。
5. 不在日志、错误报告、截图中放密钥、卡片正文、文献全文。
6. 不静默迁移数据；迁移要版本化、可回滚、有备份。
7. 不跳过“计数前后一致”的检查。
8. 不确定时停下来问，不猜参数、不猜数据。

> 宁可拒绝执行，也不要猜测性写入。数据事故的修复成本，远高于一次确认的时间成本。

## 15. 度量与节奏

| 指标 | 定义 | 目标 | 频率 |
|---|---|---|---|
| Lead time | 立项到可用 | 越短越好 | 每需求 |
| 变更失败率 | 发布导致回滚的比例 | < 10% | 每月 |
| MTTR | 故障到恢复 | < 1 小时 | 每事故 |
| 测试不稳定率 | 非确定性失败 | < 2% | 每周 |
| 关键路径 p90 | 评分到下一张 | 预算内 | 每发布 |
| 数据事故 | 损坏或丢失 | 0 | 持续 |
| 兼容事故 | 宿主升级导致高危 | 0 | 每版本 |

**单人节奏**：每日小步提交加单测，必要时部署测试 profile；每周做一次 release candidate、changelog、真机验收和备份演练；每月做依赖与宿主兼容扫描、恢复演练、指标复盘。节奏的目的是防止“攒一个大版本”，不是增加仪式。

## 19. 通用经验（与宿主无关，2026-11 从真实故障沉淀）

这一节不属于任何宿主（Anki / Zotero / 浏览器扩展都适用），每条都对应一次真实故障，写法是「症状 → 做法 → 判据」。

### 19.1 先量后改：先测出机制，再决定改哪一行

- **症状**：界面出现多余动作（窗口跳动、二次重排、闪烁），第一反应是「我们某处 resize/重绘写错了」。
- **做法**：改之前先做只读测量，把「谁触发的」变成可打印的事实。两条通道都要看：**语言层调用栈**（谁调用了你的方法）和**框架层事件**（不经过你代码的内部调用）。
- **判据**：能说出「这一步由哪个函数/哪个框架行为触发」，且有一条可重复的复现命令；说不出来就不改代码。

### 19.2 你的代码之外，框架也会动手

- **症状**：日志里没有你的调用，窗口/布局却变了。
- **做法**：框架的默认行为（布局约束、自动尺寸、焦点链、样式重算）可能在你不察觉时改变状态；覆盖方法只能截到语言层的调用，C++/内部路径必须靠事件或最终状态观测。
- **判据**：中间态能被「事件序列 + 每步的布局/几何数值」解释，而不是靠猜。

### 19.3 「关掉它」必须先证明关掉了

- **症状**：加了 `setXxx(0)`／开关置 false，现象不变。
- **做法**：任何「绕过框架」的改动，都要在**同一路径、同一起点**下重测，并打印被改的那个值本身（它可能被框架在下一轮写回）。
- **判据**：改动前后各有一组数字；若数值被写回，换实现（例如改布局约束而不是改最小尺寸），而不是加大注释说服自己。

### 19.4 拆掉安全网，要同时列出替代保障

- **症状**：为消除多余动作，关掉了框架的某条自动约束。
- **做法**：关之前先穷举「谁会依赖这条约束」，确认每条路径都由你的代码兜底；在代码注释里写明「因此所有增高路径都必须调用 X」。
- **判据**：新增路径时能一句话回答「它有没有走兜底」；否则不许拆。

### 19.5 三层身份一致：包 = 安装目录 = 正在跑的代码

- **症状**：源码改了、包装了，用户看到的却还是旧行为。
- **做法**：制品只能从**干净工作树**构建（先提交源码 → 再打包 → 产物单独提交）；发布前逐文件比对包内与安装目录。
- **判据**：包内每个文件与安装目录**逐字节相同**；「用户配置/缓存」类文件单列为数据差异，不算代码差异；运行时启动时间**晚于**所有已安装文件。

### 19.6 验证分五层，缺一层就还有未知

源码（工作树干净、HEAD 正确）→ 已部署（安装目录逐文件匹配）→ 已加载（进程启动时间晚于安装时间）→ 配置（关键项实际取值）→ 屏幕/真实交互（人眼或采样器确认）。
- **判据**：五层各有可粘贴的证据行；任何一层只能「推测」就等于没验证。

### 19.7 写用户数据：先基线、后复查、只重试「肯定没写进去」的情况

- **症状**：写操作报错，重试后出现重复记录。
- **做法**：写前记录基线（条数/最新 id），写后复查是否真的新增；只有「写前被拒绝」才允许重试一次，任何「状态未知」一律不重试。
- **判据**：能给出「基线 → 写后」的两次只读查询结果；重试分支有单测覆盖。

### 19.8 让故障可观测：钩子串联而非替换

- **症状**：用户看到报错弹窗，但本地日志没有任何记录，无法复盘。
- **做法**：安装异常钩子时保留宿主原有钩子（链式调用），安装逻辑幂等；崩溃、后台线程异常都要落到同一份日志。
- **判据**：故意抛一次异常，日志里出现完整 traceback，且宿主的原生弹窗行为不变。

### 19.9 探针只读：候选改法先在内存里试

- **症状**：为验证一个猜想直接改源码，来回部署好几次。
- **做法**：把候选改动以 monkeypatch 的形式挂在**真实调用路径**上（不改磁盘代码），跑同一套测量；证明有效再落地。
- **判据**：候选方案有「改前/改后」两组同一口径的数字；无效方案也在结论里写明为什么无效。

### 19.10 前后对比必须同口径

- **症状**：「改好了」但说不清好了多少。
- **做法**：同一个采样器、同一个起点状态、同一采样频率；记录**中间态**和最终态，而不只是结束值。
- **判据**：能报出「改前 N 次、改后 M 次」的具体次数与最大位移，而不是形容词。

### 19.11 部署是一次受控操作，不是复制文件

固定顺序：完整备份（可回滚点）→ 部署前检查（允许的唯一差异要能说清）→ 只替换指定文件（哈希前后可见）→ 礼貌重启（等空闲、不强杀）→ 重启后计数/关键数据不变 → 再跑一次检查必须全绿。
- **判据**：备份目录名、旧/新哈希、重启耗时、计数四项齐全，缺一项视为部署未完成。

### 19.12 规则要带出处

- **做法**：每条新规则都写清「它来自哪次故障、当时的数字是多少」，放在交接文档和提交信息里；只写结论的规则，下一个人会当成教条删掉。
- **判据**：半年后看到这条规则的人，能顺着证据找到当时的复现方法。
- **同一份内容只存一处**：正文只写在一个地方，其它地方只放指针（手册拥有正文、交接文档说明在哪、skill 说明何时读）。指针写法统一：同一仓库或同一盘内用相对路径；**跨出仓库或跨盘用 `%USERPROFILE%`（例：`%USERPROFILE%\.sclaw\projects\<id>\workspace\<文件>`），不写死 `C:\Users\<用户名>`**。跨盘不存在可用的相对路径，硬凑 `..\` 只会断链——本次就看到过：skill 在 C: 的用户目录、仓库在 D:，跨盘只能写仓库绝对路径（或 `%USERPROFILE%` 形式）。

### 19.13 通用检查清单（新插件/新功能上线前逐条打勾）

1. 现象能复现，且已用只读探针定位到触发点（不是猜的）。
2. 改动只碰必要文件；宿主默认行为被改动的地方，注释写明替代保障。
3. 单测全绿；宿主相关的离屏/无头界面检查全绿（偶发失败必须单跑复现并记录）。
4. 部署有可回滚备份；部署后五层验证齐全。
5. 真机前后对比有同一口径的数字，含中间态。
6. 制品从干净工作树构建，包内文件与安装目录逐字节一致。
7. 数据写入有写后校验；异常有日志；探针与临时脚本没有留在生产目录。
8. 交接文档与提交信息写清「改了什么、证据在哪、哪条规则由此而来」。
